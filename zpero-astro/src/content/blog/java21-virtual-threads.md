# Java 并发编程：JDK 21 虚拟线程，为什么可以为每个任务创建一个线程？

在前面的文章中，我们介绍了 Java 线程池的设计思想。线程池通过复用工作线程、限制线程数量和缓存等待任务，避免应用程序无限制地创建线程。

```java
ExecutorService executor = Executors.newFixedThreadPool(10);

for (int i = 0; i < 1000; i++) {
    executor.submit(() -> {
        // 执行任务
    });
}
```

这里虽然提交了 1000 个任务，但线程池最多只使用 10 个工作线程执行它们。

这样的设计非常合理，因为传统 Java 线程需要消耗操作系统资源。如果每个任务都创建一个独立线程，当任务数量不断增长时，线程创建、内存占用以及上下文切换等开销就可能成为系统的负担。

但是，JDK 21 正式引入虚拟线程（Virtual Threads）后，我们却可以这样写：

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1000; i++) {
        executor.submit(() -> {
            Thread.sleep(1000);
            return null;
        });
    }
}
```

这段代码会为每个任务创建一个虚拟线程。也就是说，1000 个任务对应 1000 个虚拟线程。这似乎与线程池的设计思想产生了矛盾。

**既然线程是一种昂贵的系统资源，为什么 JDK 21 又允许我们为每个任务创建一个线程？**

要回答这个问题，首先需要理解传统 Java 线程究竟昂贵在哪里。

## 一、传统 Java 线程为什么昂贵？

### 1.1 Java 线程与操作系统线程

在传统的 Java 线程模型中，Java 平台线程（Platform Thread）通常与操作系统线程一一对应。

```
Thread thread = new Thread(() -> {
    System.out.println("执行任务");
});

thread.start();
```

当我们启动这个线程时，JVM 会通过操作系统提供的线程机制创建对应的执行资源。

可以简化理解为：

```
Java Platform Thread
          │
          ▼
    操作系统线程
          │
          ▼
       CPU 执行
```

这里的关键在于： **Java 平台线程通常需要占用一个操作系统线程。** 操作系统线程需要维护自己的执行上下文、栈空间以及调度相关的信息。 当线程数量增加时，系统就需要承担更多资源开销。例如：

- 线程栈占用内存。
- 操作系统需要管理大量线程。
- 线程切换可能产生调度开销。
- 大量线程竞争 CPU 时，运行效率可能下降。

因此，传统 Java 应用通常不会为每个任务都无限制地创建平台线程。

### 1.2 为什么需要线程池？

假设系统需要处理 10000 个任务。如果每个任务都创建一个平台线程，那么可能需要创建 10000 个操作系统线程。这通常不是一个合理的设计。因此，我们使用线程池：

```
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10,
    20,
    60,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),
    new ThreadPoolExecutor.AbortPolicy()
);
```

线程池通过限制工作线程数量，控制操作系统线程资源的消耗。当任务数量超过工作线程的处理能力时，任务进入等待队列。但这又引出了一个问题。

**线程池限制的是线程数量，并不意味着所有线程都在充分利用 CPU。**

## 二、为什么线程池中的线程可能被浪费？

考虑下面的代码：

```
public String query() {
    return remoteService.call();
}
```

假设 `remoteService.call()` 是一次同步 HTTP 请求，需要等待远程服务器返回结果。

执行过程可能是：

```
工作线程
   │
   ▼
发送 HTTP 请求
   │
   ▼
等待远程响应
   │
   ▼
获取响应结果
   │
   ▼
继续执行
```

在等待远程响应期间，线程并没有持续执行有用的 Java 计算。但是，在传统阻塞式 I/O 模型中，这个工作线程通常仍然被当前任务占用。

- 线程池有 20 个工作线程。
- 每个任务都需要等待远程接口 1 秒。
- 这些任务大部分时间都在等待 I/O。

那么即使 CPU 还有大量空闲资源，线程池也可能因为 20 个工作线程都在等待而无法继续处理更多任务。新的任务只能排队。问题在于：

**CPU 并不忙，但能够承载任务的工作线程已经用完了。**这也是传统阻塞式 I/O 服务容易受到线程数量限制的原因之一。

### 2.1 能不能直接增加线程数量？

当然可以。例如，把线程池从 20 个线程扩大到 200 个线程。这样就可以让更多任务同时等待 I/O。但线程数量继续增加，操作系统线程的资源开销也会随之增长。因此，我们遇到了一个矛盾：

> 为了提高阻塞式 I/O 任务的并发能力，需要更多线程；但创建大量操作系统线程又会带来资源压力。

虚拟线程就是为了解决这个矛盾而设计的。

## 三、虚拟线程是什么？

JDK 21 通过 JEP 444 正式引入虚拟线程。虚拟线程仍然是 Java 的 `Thread`。但与传统平台线程不同，**虚拟线程不需要在整个生命周期中独占一个操作系统线程。**它由 JVM 负责调度，可以在数量相对较少的平台线程上运行大量虚拟线程。

这些用于执行虚拟线程的平台线程通常被称为：**载体线程（Carrier Thread）。**可以将两种模型进行对比。

### 3.1 传统平台线程模型

```
Platform Thread A ── OS Thread A
Platform Thread B ── OS Thread B
Platform Thread C ── OS Thread C
Platform Thread D ── OS Thread D
```

平台线程通常与操作系统线程一一对应。

### 3.2 虚拟线程模型

```
Virtual Thread A ──┐
Virtual Thread B ──┤
Virtual Thread C ──┤
Virtual Thread D ──┼── JVM 调度器
Virtual Thread E ──┤        │
Virtual Thread F ──┘        │
                      ┌─────┴─────┐
                      ▼           ▼
                   Carrier 1   Carrier 2
                      │           │
                      ▼           ▼
                  OS Thread 1  OS Thread 2
```

这张图表达的是一种多对少的调度关系。

大量虚拟线程可以由较少的载体线程轮流执行。

但需要注意：

**一个载体线程在某一时刻通常只执行一个虚拟线程。**

虚拟线程并没有让一个 CPU 核心同时执行无限多个计算任务。

它的优势在于，当虚拟线程遇到可卸载的阻塞操作时，可以释放载体线程，让载体线程继续执行其他虚拟线程。

## 四、虚拟线程如何实现阻塞而不长期占用载体线程？

这是理解虚拟线程最重要的一部分。

假设一个虚拟线程正在执行：

```
Thread.sleep(1000);
```

对于平台线程而言，调用 `sleep()` 会使对应的平台线程进入休眠状态。

而对于虚拟线程，JVM 可以采用不同的处理方式。

### 4.1 虚拟线程的挂载

当虚拟线程开始运行时，JVM 调度器会将它安排到某个载体线程上执行。

这个过程称为：

**挂载（Mount）。**

```
Virtual Thread A
       │
       ▼
   Mount
       │
       ▼
Carrier Thread 1
       │
       ▼
执行 Java 代码
```

此时虚拟线程正在使用载体线程执行任务。

### 4.2 遇到阻塞操作时卸载

假设虚拟线程执行：

```
Thread.sleep(1000);
```

JVM 可以暂停这个虚拟线程，并将其从载体线程上卸载。

这个过程称为：

**卸载（Unmount）。**

```
Virtual Thread A
       │
       ▼
执行 Thread.sleep()
       │
       ▼
保存继续执行所需的状态
       │
       ▼
Unmount
       │
       ├── Virtual Thread A 等待
       │
       ▼
Carrier Thread 1 被释放
       │
       ▼
执行 Virtual Thread B
```

此时，虚拟线程 A 仍然存在，只是暂时不需要占用载体线程。

载体线程可以继续执行其他虚拟线程。

当等待时间结束后，虚拟线程 A 重新变为可运行状态。

调度器会在合适的时机将它挂载到某个载体线程上，继续执行。

这个载体线程不一定是之前的 Carrier Thread 1。

### 4.3 虚拟线程并不是不会阻塞

这里需要特别强调：

**虚拟线程仍然可以阻塞，只是某些阻塞操作不再需要长期占用底层载体线程。**

例如：

```
Thread.sleep(1000);
```

从虚拟线程自己的视角看，它确实等待了 1 秒。

但从载体线程的视角看，它可以在这段时间执行其他虚拟线程。

因此：

```
虚拟线程阻塞
      ≠
载体线程一定阻塞
```

这是虚拟线程能够支持大量并发等待任务的关键。

不过，并不是所有阻塞操作都能卸载虚拟线程。

这一点后面还会讨论。

## 五、虚拟线程的底层是如何实现的？

前面提到，虚拟线程在阻塞时可以卸载，并在之后恢复执行。

但这又产生了一个问题：

**线程执行到一半，JVM 如何保存它的执行状态，并在之后继续执行？**

答案与虚拟线程的栈管理机制有关。

### 5.1 传统线程栈

传统平台线程具有与其执行环境关联的线程栈。

方法调用会在栈上形成相应的栈帧。

例如：

```
public void methodA() {
    methodB();
}

public void methodB() {
    methodC();
}

public void methodC() {
    Thread.sleep(1000);
}
```

执行关系：

```
methodA()
   │
   ▼
methodB()
   │
   ▼
methodC()
   │
   ▼
Thread.sleep()
```

当线程执行到 `sleep()` 时，方法调用状态仍然需要保留。

对于平台线程，这些执行状态与它对应的操作系统线程栈密切关联。

### 5.2 虚拟线程的栈可以被保存和恢复

虚拟线程采用不同的栈管理方式。

在 JDK 21 的 HotSpot 实现中，虚拟线程的执行状态可以通过 Continuation（续体）机制保存和恢复。

虚拟线程的栈帧可以存储在 Java 堆中的栈块（Stack Chunk）中。

当虚拟线程需要卸载时，JVM 可以保留它的执行状态，而不要求一个载体线程始终为它保留运行位置。

之后重新挂载时，再恢复执行。

可以简化理解为：

```
虚拟线程正在执行
       │
       ▼
遇到可卸载的阻塞点
       │
       ▼
保存执行状态
       │
       ▼
释放载体线程
       │
       ▼
等待条件满足
       │
       ▼
重新挂载
       │
       ▼
恢复之前的执行位置
```

这里需要注意，虚拟线程不是简单地把一个操作系统线程的完整栈复制到堆中。

实际实现涉及 Continuation、栈块、栈帧管理以及 JVM 的运行时机制。

因此，虚拟线程能够以不同于传统平台线程的方式管理执行状态。

### 5.3 虚拟线程如何调度？

在 JDK 21 中，虚拟线程默认由 JVM 使用的调度器执行。

该调度器基于 `ForkJoinPool`，使用平台线程作为载体线程。

默认调度并行度通常与可用处理器数量有关，也可以通过 JVM 属性进行配置，例如：

```
-Djdk.virtualThreadScheduler.parallelism=8
```

但不要把这个参数理解成“最多只能创建 8 个虚拟线程”。

它主要影响默认调度器的目标并行度，而不是虚拟线程数量上限。

**虚拟线程数量与同时执行 Java 代码的载体线程数量，是两个不同的概念。**

## 六、JDK 21 如何创建虚拟线程？

### 6.1 Thread.startVirtualThread()

最简单的方式：

```
Thread thread = Thread.startVirtualThread(() -> {
    System.out.println("当前线程：" + Thread.currentThread());
});
```

这个方法会创建并启动一个虚拟线程。

可以通过：

```
Thread.currentThread().isVirtual()
```

判断当前线程是否为虚拟线程。

例如：

```
Thread thread = Thread.startVirtualThread(() -> {
    System.out.println(Thread.currentThread().isVirtual());
});

thread.join();
```

输出：

```
true
```

### 6.2 Thread.ofVirtual()

也可以使用构建器：

```
Thread thread = Thread.ofVirtual()
    .name("virtual-task-1")
    .start(() -> {
        System.out.println("执行任务");
    });

thread.join();
```

这种方式可以为虚拟线程设置名称等属性。

### 6.3 使用虚拟线程执行器

对于大量独立任务，更常见的方式是：

```
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {

    for (int i = 0; i < 1000; i++) {
        executor.submit(() -> {
            Thread.sleep(1000);
            return null;
        });
    }
}
```

`newVirtualThreadPerTaskExecutor()` 会为每个提交的任务创建一个新的虚拟线程。

它与传统固定线程池有明显区别。

传统固定线程池：

```
1000 个任务
     │
     ▼
10 个工作线程反复执行
     │
     ▼
其他任务排队
```

虚拟线程执行器：

```
1000 个任务
     │
     ▼
创建 1000 个虚拟线程
     │
     ▼
由调度器安排到载体线程运行
```

这里还要注意：

`try-with-resources` 结束时会关闭执行器，并等待已提交任务结束。

因此，这段示例代码不是提交完任务后立即退出。

## 七、虚拟线程与线程池是什么关系？

既然虚拟线程创建成本更低，那么是否还需要线程池？首先需要区分两个概念：

**线程池复用线程，虚拟线程执行器通常不复用虚拟线程。**

### 7.1 传统线程池为什么复用线程？

传统平台线程的创建和维护成本较高。因此，线程池会尽量复用已有工作线程。例如：

```
ExecutorService executor = Executors.newFixedThreadPool(10);
```

无论提交多少任务，正常情况下都由最多 10 个工作线程反复执行。

### 7.2 为什么不建议池化虚拟线程？

虚拟线程的设计目标之一，就是让创建一个线程来执行一个任务变得足够便宜。

因此，通常没有必要再维护一个固定数量的虚拟线程池。

推荐的使用方式是：

```
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(task1);
    executor.submit(task2);
    executor.submit(task3);
}
```

每个任务拥有自己的虚拟线程。

任务执行完成后，对应的虚拟线程也结束。

这里不是复用虚拟线程，而是让 JVM 在底层调度器中复用载体线程等执行资源。

### 7.3 虚拟线程不意味着可以无限制地执行任务

假设某个系统需要访问数据库。

数据库连接池最多只有 20 个连接。

即使我们创建了 10000 个虚拟线程，也不意味着数据库可以同时处理 10000 个查询。

大量虚拟线程可能仍然需要等待数据库连接。

因此：

**虚拟线程降低的是线程资源的成本，并没有消除数据库、网络、CPU 等其他资源的容量限制。**

如果需要限制某个操作的并发数量，可以使用 `Semaphore`。

例如：

```
Semaphore semaphore = new Semaphore(20);

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {

    for (int i = 0; i < 1000; i++) {
        executor.submit(() -> {
            semaphore.acquire();
            try {
                performOperation();
            } finally {
                semaphore.release();
            }
            return null;
        });
    }
}
```

这里创建了大量虚拟线程，但最多只允许 20 个任务同时进入受保护的操作。

这与传统线程池通过限制线程数量来间接限制并发的思路不同。

**虚拟线程负责承载任务，Semaphore 负责限制特定资源的并发访问。**

## 八、虚拟线程与 CompletableFuture 有什么区别？

前面我们已经学习过 `CompletableFuture`。它能够通过 `thenApply()`、`thenCompose()`、`thenCombine()` 等方法组织异步任务。那么，有了虚拟线程，是否就不再需要 `CompletableFuture`？

答案是否定的。因为它们解决的问题不同。

### 8.1 CompletableFuture：关注任务之间的依赖

例如：

```
CompletableFuture<Integer> a =
    CompletableFuture.supplyAsync(() -> 10, executor);

CompletableFuture<Integer> b =
    a.thenApply(x -> x * 2);
```

这里的重点是：

任务 A 完成后，如何将结果传递给任务 B。

### 8.2 虚拟线程：关注任务的执行成本

例如：

```
Thread.startVirtualThread(() -> {
    int a = calculateA();
    int b = calculateB(a);
    System.out.println(b);
});
```

这里可以直接使用顺序代码表达依赖关系。

如果任务在等待 I/O 时能够卸载，底层载体线程就可以继续执行其他虚拟线程。

因此，虚拟线程能够让某些过去需要通过回调或异步 API 编写的代码，重新使用更直观的同步写法。

但这并不意味着 `CompletableFuture` 失去了价值。

当我们需要：

- 表达复杂的任务依赖图。
- 对多个异步结果进行组合。
- 为异步计算注册后续处理。
- 与已有的异步 API 集成。

`CompletableFuture` 仍然非常有用。

两者的区别可以概括为：

| 对比             | CompletableFuture  | 虚拟线程                       |
| ---------------- | ------------------ | ------------------------------ |
| 主要目标         | 异步任务编排       | 降低线程资源成本               |
| 核心能力         | 结果传递、依赖组合 | 轻量线程、阻塞时可卸载         |
| 编程方式         | 回调、任务链       | 顺序式代码                     |
| 是否需要执行器   | 异步阶段通常需要   | JVM 调度器负责运行             |
| 是否自动消除阻塞 | 否                 | 对支持的阻塞操作可释放载体线程 |

**CompletableFuture 解决的是任务如何协作，虚拟线程解决的是任务如何以较低线程成本执行。**

## 九、虚拟线程有哪些局限？

虚拟线程并不是没有成本，也不是所有阻塞操作都能让载体线程得到释放。

其中一个重要问题是：

**Pinning（固定或钉住载体线程）。**

### 9.1 什么是 Pinning？

正常情况下，虚拟线程遇到支持卸载的阻塞操作时，可以从载体线程上卸载。

但在 JDK 21 中，某些情况下虚拟线程无法卸载。

例如，在持有 `synchronized` 监视器期间发生阻塞。

考虑下面的代码：

```
private static final Object LOCK = new Object();

public static void execute() throws InterruptedException {
    synchronized (LOCK) {
        Thread.sleep(1000);
    }
}
```

如果这段代码由虚拟线程执行，那么在 JDK 21 中，虚拟线程可能因为持有监视器而无法卸载。

结果就是：

```
Virtual Thread A
       │
       ▼
进入 synchronized
       │
       ▼
执行 Thread.sleep()
       │
       ▼
虚拟线程阻塞
       │
       ▼
Carrier Thread 也被占用
```

这就削弱了虚拟线程在大量阻塞任务场景中的优势。

需要注意，**Pinning 是 JDK 21 特定实现行为的重要限制**，后续 JDK 已经针对 `synchronized` 导致的 Pinning 进行了改进，不能把这一结论不加区分地套用到所有 Java 版本。

### 9.2 synchronized 不能用了吗？

不是。

`synchronized` 仍然可以在虚拟线程中使用。

真正需要关注的是：

**是否在持有监视器期间执行长时间阻塞操作。**

如果临界区只是简单修改共享变量：

```
synchronized (LOCK) {
    count++;
}
```

通常没有必要仅仅因为使用虚拟线程就将它改写。

但如果临界区中存在耗时 I/O 或长时间等待，在 JDK 21 中就值得检查是否会发生 Pinning。

对于确实需要在临界区中阻塞的场景，可以评估是否适合使用 `ReentrantLock` 等其他同步机制。

不过，替换锁之前仍然应该先检查锁的必要性和临界区设计，而不是机械地将所有 `synchronized` 替换掉。

### 9.3 如何排查 Pinning？

JDK 21 提供了相关诊断能力。

例如：

```
-Djdk.tracePinnedThreads=full
```

当虚拟线程在某些被固定的情况下发生阻塞时，JVM 可以输出相关堆栈信息。

也可以借助 JDK Flight Recorder（JFR）分析 `jdk.VirtualThreadPinned` 等事件。

这些工具有助于发现虚拟线程无法卸载的阻塞位置。

### 9.4 虚拟线程适合 CPU 密集型任务吗？

假设我们执行大量纯计算任务：

```
Thread.startVirtualThread(() -> {
    long result = 0;

    for (long i = 0; i < 1_000_000_000L; i++) {
        result += i;
    }

    System.out.println(result);
});
```

这种任务主要消耗 CPU。

虚拟线程不会让 CPU 的计算能力凭空增加。

如果大量虚拟线程持续执行 CPU 密集型计算，仍然需要竞争有限的 CPU 核心。

因此，虚拟线程最有代表性的优势是：

**在大量任务需要等待 I/O 的场景中，提高线程资源利用率和并发承载能力。**

对于 CPU 密集型任务，传统固定大小的线程池仍然是值得考虑的选择。

## 十、虚拟线程会带来哪些新的问题？

### 10.1 不要使用 ThreadLocal 缓存昂贵资源

虚拟线程仍然支持 `ThreadLocal`。但如果每个任务都创建一个新的虚拟线程，那么每个虚拟线程也可能拥有独立的线程局部变量。

例如：

```
private static final ThreadLocal<byte[]> BUFFER =
    ThreadLocal.withInitial(() -> new byte[1024 * 1024]);
```

如果大量虚拟线程都初始化一个 1MB 的缓冲区，就可能造成很高的内存占用。传统线程池中的工作线程会被复用，因此某些程序习惯使用 `ThreadLocal` 缓存对象。但虚拟线程通常是任务执行完毕后就结束，不适合沿用所有依赖线程长期复用的设计。

### 10.2 虚拟线程不是越多越好

虚拟线程比平台线程轻量，但仍然需要内存保存对象和执行状态。大量虚拟线程还可能带来：

- 堆内存占用增长。
- 任务对象和上下文数据积压。
- 下游资源竞争。
- 超时与取消管理复杂化。

因此，不能把“可以创建大量虚拟线程”理解为“可以无限制创建任务”。

### 10.3 注意任务生命周期

虚拟线程不意味着任务可以不受管理地运行。

例如：

```
Thread.startVirtualThread(() -> {
    performOperation();
});
```

这个虚拟线程启动后，调用者不一定知道它什么时候结束、是否发生异常。

此外，虚拟线程是守护线程，不能依赖它们阻止 JVM 退出。

因此，实际开发中仍然需要管理任务生命周期。

对于一组相关任务，可以使用执行器，并在适当位置等待任务完成。

JDK 21 还提供了预览版的结构化并发 API，但在 JDK 21 中使用它需要启用预览特性，不能将其视为普通的正式稳定 API。

## 十一、什么时候应该使用虚拟线程？

虚拟线程比较适合以下类型的任务：

- 大量同步 HTTP 调用。
- 大量数据库访问。
- 大量阻塞式网络 I/O。
- 需要保持同步代码风格的高并发服务。

但实际收益取决于使用的库是否能够与虚拟线程良好协作，以及系统瓶颈是否主要来自平台线程资源。

如果系统本身已经使用高效的非阻塞事件驱动模型，虚拟线程不一定带来明显提升。

如果瓶颈是 CPU、数据库吞吐量或外部服务限流，增加虚拟线程数量也无法直接解决这些问题。

因此，判断是否使用虚拟线程，应该先回答：

**系统当前的并发能力，究竟是受到线程资源限制，还是受到其他资源限制？**

如果大量平台线程长期阻塞等待 I/O，虚拟线程就可能带来明显价值。

如果系统主要受 CPU 或下游资源容量限制，那么虚拟线程的收益可能有限。

## 十二、总结

回到文章最初的问题：

**为什么传统线程池需要限制线程数量，而 JDK 21 却允许我们为每个任务创建一个虚拟线程？**

原因在于，两者管理的线程资源成本不同。

传统平台线程通常与操作系统线程一一对应。

创建大量平台线程，会带来较高的内存和操作系统调度成本。

因此，我们需要通过线程池复用工作线程，限制平台线程数量。

而虚拟线程由 JVM 管理，可以在较少的载体线程上运行大量虚拟线程。

当虚拟线程遇到支持卸载的阻塞操作时，JVM 可以保存它的执行状态，并释放载体线程去执行其他虚拟线程。

因此，虚拟线程能够降低大量并发等待任务对操作系统线程资源的占用。

它的核心机制可以概括为：

1. **轻量化**：虚拟线程不需要在整个生命周期中独占操作系统线程。
2. **挂载与卸载**：虚拟线程可以在载体线程上运行，并在合适的阻塞点卸载。
3. **执行状态保存**：通过 Continuation 等机制保存和恢复执行状态。
4. **JVM 调度**：由调度器将大量虚拟线程安排到较少的载体线程上运行。
5. **按任务创建线程**：通常无需复用虚拟线程，而是为每个任务创建独立的虚拟线程。

但虚拟线程并没有消除所有资源限制。

它不能增加 CPU 的计算能力，也不能突破数据库连接池和外部服务的吞吐量上限。

在 JDK 21 中，还需要特别关注 Pinning、`ThreadLocal` 使用以及任务生命周期管理等问题。

最后可以用一句话总结：

> **传统线程池通过减少线程数量来控制成本，而虚拟线程通过降低单个线程的资源成本，让大量并发任务可以继续使用直观的同步编程模型。**

虚拟线程的意义，并不是简单地让 Java 可以创建更多线程，而是让“一个任务对应一个线程”重新成为高并发 I/O 场景中可行的编程方式。
