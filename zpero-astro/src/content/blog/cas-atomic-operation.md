# CAS 是如何实现原子操作的？

在多线程环境中，当多个线程同时修改一个共享变量时，如何保证修改结果的正确性？

在`有了volatile为什么还要加锁` 文章中，我们提到：`volatile` 可以保证可见性和一定的有序性，但无法保证复合操作的原子性。

[有了 volatile 为什么还要加锁？](https://zpero-site.pages.dev/blog/volatile-why-lock/)

例如：

```
volatile int count = 0;
```

线程 A 和线程 B 同时执行：

```
count++;
```

由于 `count++` 包含读取、计算和写入三个步骤，两个线程可能读取到相同的旧值，最终造成更新丢失。

| 步骤 | 线程 A       | 线程 B       | count |
| ---- | ------------ | ------------ | ----- |
| 1    | 读取 0       | —            | 0     |
| 2    | —            | 读取 0       | 0     |
| 3    | 计算并写入 1 | —            | 1     |
| 4    | —            | 计算并写入 1 | 1     |

对于这个问题，我们可以通过 `synchronized` 加锁，使同一时刻只有一个线程执行自增操作。

但是，**如果不使用互斥锁，能否保证共享变量被正确更新？**

我们不妨换一种思路。

既然多个线程同时读取旧值会导致更新丢失，那么在写入之前，能不能**先判断共享变量是否仍然等于之前读取到的值**？

如果相等，就尝试写入新值；如果不相等，说明当前值已经发生变化，需要重新读取并计算。

不过，这种方案还有一个问题：

```
if (count == expected) {
    count = newValue;
}
```

假设线程 A 判断 `count == expected` 成立，但还没来得及写入，线程 B 就修改了 `count`。

此时线程 A 继续写入，依然可能覆盖线程 B 的修改。

**所以，问题的关键不只是比较之后再更新，而是必须保证比较和更新这两个动作不可分割。**

这就是 CAS（Compare-And-Swap，比较并交换）要解决的问题。



## 1. CAS 是什么？

**CAS（Compare-And-Swp）** 是并发编程的原子操作，通过比较当前共享变量的预期值和实际值是否一致，决定是否将变量更新为新值。

核心思路是：

**只有实际值和预期值一致的时候，才允许更新，否则不更新。**

CAS（V，E，N） 的三个参数：

- Value：要修改的变量
- Expected：预期值，线程认为当前应该具有的值。
- New： 准备写入的新值

## 2. CAS如何保证原子性？



继续使用计数器count++ 的例子：

假设 `count = 0`，线程 A 和线程 B 都希望将它加 1。

两个线程最初都读取到 `count = 0`，并计算出新值 1。

这次我们不直接执行赋值，而是使用 CAS。

| 步骤 | 线程 A         | 线程 B           | count |
| :--: | :------------- | :--------------- | :---: |
|  1   | 读取预期值 0   | 读取预期值 0     |   0   |
|  2   | CAS(0, 1) 成功 | —                |   1   |
|  3   | —              | CAS(0, 1) 失败   |   1   |
|  4   | —              | 重新读取预期值 1 |   1   |
|  5   | —              | CAS(1, 2) 成功   |   2   |

### 2.1 为什么两个线程不能同时成功？

因为CAS 是比较和更新的原子操作，对于同一个变量，两个线程都要将count 从 0 修改为1 时，只有一个线程能基于0 的状态进行修改。

另一个线程CAS 时会发现 count 已经不再是 0 了，写入1 的操作就会失败。

这就避免了count ++ 中两个线程基于同一个旧值重复写入的问题。

### 2.2 CAS失败后会重试吗？

不会，**CAS 只负责一次比较和更新，并返回操作是否成功**。

如果CAS 失败，是否重新读取、重新计算、重新更新取决于调用方的实现

一般计数器自增，一般使用循环不断充实直到成功。这种  <u>通过 CAS 失败后重新反复尝试更新的方式 ，成为CAS 自旋重试</u>。

**CAS 是原子操作，自旋是围绕CAS 构建的重试策略，两者不是一个概念。**



## 3. CAS 底层原理

前面我们知道，普通的 `if` 判断加赋值无法保证原子性，而 CAS 可以。

说明**CAS 的机制不由代码提供，而是硬件提供的底层原子性造作保证**

### 3.2 CPU 如何实现CAS？

现代cpu 提供了 读-改-写的指令或指令序列，常见的x86芯片为例，通过 CMPXCHG（compare and exchange） 指令实现比较交换

对于多个cpu，可能同时访问共享内存，通常要配合LOCK 等前缀保证原子性

工作流程是：

1. cpu 读取目标内存位置的值
2. 将当前值和预期值比较
3. 如果相等，将新值写入目标位置
4. 如果不想等，保留原值

这些步骤通过一个硬件的原子操作完成，不会出现java 判断和复制之间的 竞争窗口

**CAS 的原子性源自 CPU 提供的 读- 改- 写 原子性，不是Volatile本身**



### 3.3 Java 如何调用底层CAS？

Java 程序通常不需要直接调用cpu指令，而是通过JDK提供的原子类 使用CAS

例如 ：

```java
AtomicInteger count  = new AtomicInteger(0);
boolean success = count.compareAndSet(0.1);
```

现代JDK中，AtomicInteger 可以通过 varHandle 等底层机制实现原子操作

```text
Java 应用代码
      ↓
AtomicInteger.compareAndSet()
      ↓
VarHandle / JVM 原子操作支持
      ↓
平台相关的原子操作实现
      ↓
CPU 原子指令
```

JVM 会根据平台选择相应的实现方式，开发Java程序时不需要关心硬件底层的实现，可以直接使用CAS



## 4. AtomicInteger 如何实现原子自增？

Java 在  Java.util.concurrent.atmic 包下面定义了几个 原子类：

- `AtomicInteger`
- `AtomicLong`
- `AtomicReference`
- `AtomicBoolean`

例如：

```java
import java.util.concurrent.atomic.AtomicInteger;

public class Counter {

    private final AtomicInteger count =
            new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet();
    }

    public int getCount() {
        return count.get();
    }
}
```

及时多个线程调用increment（） 也不会发生更新丢失的问题



为了理解它的工作原理，可以使用下面的 CAS 循环作为示意：

```java
public int increment() {
    int expected;
    int next;

    do {
        expected = count.get();
        next = expected + 1;
    } while (!count.compareAndSet(expected, next));

    return next;
}
```

另外，`AtomicInteger` 的原子操作还具有相应的内存语义。例如，`compareAndSet()` 具有 volatile 读写的内存效果。

因此，CAS 和 volatile 并不是相互替代的关系，而是可以共同构成 Java 原子类的实现基础。




## 5. CAS 能力边界

### 5.1 ABA 问题

假设一个共享变量的初值是A ，线程 1 要执行 CAS（A，C） ， 线程2 要执行 CAS（A，B）+ CAS（B，A）并且先于 线程1 执行。

对于 线程1 来讲，共享变量的当前值仍是A， 满足CAS 的条件， 但是 共享变量 实际上已经发生了一次变化

**这就是 ABA 问题：CAS 只能比较当前值，无法仅凭当前值判断变量是否曾经发生过变化。**

现在常用的解决方案 是 **引入版本号**：

原来只比较   CAS （A , C）

现在要比较    预期值（A，Version=1） ，  当前值 （A，version=3）}

### 5.2 高竞态条件的重试开销

在竞争较低时，CAS 可以避免传统互斥锁带来的部分协调开销。

但在竞争激烈时，反复重试会消耗 CPU 资源，还可能引起缓存行竞争。

因此，**CAS 并不意味着一定比加锁快。**



例如， 高并发计数条件下，Java提供了 LongAdder ， 通过分散热点更新来降低竞争，通常比所有线程都更新同一个AtomicLong 更适合高竞态计数场景



### 5.3 多个共享变量的一致性问题（多CAS操作的任务单元有未完成的风险）

对于一个银行账户转账来说：

```java
int balanceA =  100;
int balanceB  = 100;
```

从A 向 B 转 50块钱 ， 

```java
balanceA -= 50;
balanceB += 50；
```

我们希望这个操作是一个整体

```java
CAS(balanceA, 100 , 50);
CAS(balanceB, 100,  150);
```

连贯操作被分成了两个CAS ， **CAS只能保证单变量的读-改- 写 的原子性， 多变量可能会出现未完成的中间态。**（单一变量操作原子性）

因此，对于业务场景来说，**互斥锁仍然是维护一致性的必要解决方案。**



### 6. CAS和锁如何选择？

CAS 采用乐观的更新思路：不预先排斥其他线程，而是在提交更新时检查共享状态是否符合预期。

锁则通过互斥机制，限制其他线程进入受同一把锁保护的临界区。

| 对比     | CAS                                             | synchronized                   |
| -------- | ----------------------------------------------- | ------------------------------ |
| 核心思想 | 比较并乐观更新                                  | 互斥访问                       |
| 竞争失败 | 返回失败结果，可由调用方重试                    | 重新获取锁                     |
| 线程阻塞 | 单次CAS操作不会因竞争而阻塞，反复重试会导致阻塞 | 获取锁时可能阻塞               |
| 适用场景 | 简单更新，原子计数                              | 多步操作，复杂共享状态         |
| 主要问题 | ABA、反复重试的CPU开销、多步操作一致性问题      | 锁竞争资源消耗、阻塞及协调开销 |



## 7. 总结

回到文章最初的问题：

**如果不使用传统互斥锁，能不能保证共享变量被正确更新？**

CAS 给出了一种解决思路：

线程先读取共享变量的当前值，计算出新值，然后通过原子的比较交换操作尝试更新。

如果当前值仍然符合预期，就完成更新；否则更新失败，由调用方决定是否重新尝试。

CAS 的核心并不在于循环重试，而在于**比较和更新作为一个不可分割的原子操作执行**。

在 Java 中，`AtomicInteger` 等原子类利用底层原子操作机制，为简单共享状态更新提供了方便的线程安全实现。

但 CAS 也存在能力边界：它无法仅凭当前值识别 ABA 变化历史，高竞争下可能产生大量重试，并且不能直接保证多个独立共享变量之间的整体一致性。

因此，CAS 与锁并不是谁取代谁的关系，而是针对不同并发场景提供的解决方案。

理解 CAS，最重要的是理解三个问题：

1. **为什么普通的判断加赋值不能保证原子性？**
2. **为什么底层 CAS 可以保证比较和更新不可分割？**
3. **为什么 CAS 能实现原子更新，却仍然不能解决所有线程安全问题？**

弄清楚这三个问题，就理解了 CAS 在 Java 并发编程中的核心作用。
