# 从 CAS 到 AQS，一把锁是如何实现的？

在上一篇 CAS 文章中，我们介绍了如何通过原子的比较交换操作，在不使用传统互斥锁的情况下安全更新共享变量。

既然 CAS 已经能够保证共享变量更新的原子性，那么我们能否利用 CAS 自己实现一把锁？

假设使用一个共享变量 `state` 表示锁的状态：

- `state = 0`：锁未被占用。
- `state = 1`：锁已被占用。

当线程需要获取锁时，通过 CAS 尝试将 `state` 从 0 修改为 1。

```java
private final AtomicInteger state = new AtomicInteger(0);

public void lock() {
    while (!state.compareAndSet(0, 1)) {
        // 获取失败，继续尝试
    }
}

public void unlock() {
    state.set(0);
}
```

这里的代码只是一个简化的自旋锁示例，暂时忽略锁持有者校验、可重入性等问题，不能直接作为生产环境中的锁使用。

假设线程 A 和线程 B 同时尝试获取锁。

线程 A 先执行 CAS，成功将 `state` 从 0 修改为 1，获得锁并进入临界区。

此时线程 B 也尝试获取锁，但由于 `state = 1`，CAS 操作失败，只能继续循环重试。

| 步骤 | 线程 A         | 线程 B         | state |
| ---- | -------------- | -------------- | :---: |
| 1    | CAS(0, 1) 成功 | —              |   1   |
| 2    | 进入临界区     | CAS(0, 1) 失败 |   1   |
| 3    | 执行业务逻辑   | 不断重试 CAS   |   1   |
| 4    | 释放锁         | 继续尝试       |   0   |
| 5    | —              | CAS(0, 1) 成功 |   1   |

这种方式确实可以实现最基本的互斥访问，但存在一个明显的问题：

**如果线程 A 长时间不释放锁，线程 B 就会一直执行 CAS，不断消耗 CPU 资源。这也就是CAS 的资源消耗缺陷**

对于持有时间很短的锁，自旋可能是一种合理的选择。但如果锁竞争激烈，或者临界区执行时间较长，持续自旋就可能造成不必要的资源消耗。

那么我们换一种思路：

**当线程获取锁失败时，不再让它一直自旋，而是先把它放入等待队列，并在适当的时候挂起。等到持锁线程释放锁后，再通知等待线程重新尝试获取。**

这样就需要考虑几个问题：

1. 怎么管理多个等待获取锁的线程？
2. 等待所的过程中，如何安全的挂起和唤醒线程？
3. 如何协调同步状态的更新和等待队列的维护？

这正是 **AQS（AbstractQueuedSynchronizer，抽象队列同步器）** 所提供的基础能力。

## 2. AQS 是什么？

AQS是  **JUC** java.util.concurrent.lock  包中的抽象类，为锁和其他同步工具提供了一套通用的实现框架

例如：

- `ReentrantLock`：可重入互斥锁。
- `Semaphore`：信号量。
- `CountDownLatch`：倒计时门闩。
- `ReentrantReadWriteLock`：读写锁。

这些同步工具的业务语义不同，但都需要处理一些共同的问题：同步状态的管理、线程竞争、等待与唤醒。

AQS 将这些通用机制抽象出来，而具体的同步规则由不同的同步器实现。



例如，对于 `ReentrantLock`，同步状态可以表示锁的重入次数；对于 `Semaphore`，同步状态可以表示可用许可数量。

因此，**AQS 本身并不是一把锁，而是用于构建锁和其他同步器的基础框架。**

理解 AQS，可以先抓住三个核心部分：

- 同步状态 `state`
- CAS 原子操作
- 同步等待队列

## 3. AQS 的核心组成

### 3.1 State ： 同步状态

AQS 内部维护了一个关键字段：

```java
private volatile int state;
```

`state` 用于记录当前同步器的状态。

它的具体含义不是固定的，而是由AQS 的同步器决定。

以 ReentrantLock为例，



| state | 含义                         |
| ----- | ---------------------------- |
| 0     | 锁未被持有                   |
| 1     | 被持有一次                   |
| 2     | 同一线程重入后，持有次数为 2 |
| n     | 同一线程持有锁n次            |

这里的 `state` 使用 `volatile` 修饰，保证线程对同步状态的读取具有相应的可见性与有序性。

但是仅有volatile不够，多个线程可能同时尝试修改state，我们还需要保证状态更新的原子性。

### 3.2 CAS：原子更新State

AQS 提供了 `compareAndSetState()` 方法，用于原子地修改同步状态。

```java
compareAndSetState(0, 1);
```

假设两个线程同时获取一把空闲的锁，线程A 和 B 都希望把state 从 0 改为1：

由于CAS 的原子性，只有一个线程能完成state 的更新。

这样，我们就可以利用 CAS 来协调多个线程对同步状态的竞争。

不过，需要注意，**AQS 并不是所有状态修改都必须通过 CAS 完成**。 例如，某些同步器在已经确认当前线程独占持有锁的情况下，可以直接更新 `state`。

CAS 主要用于需要原子竞争或协调的状态更新。

### 3.3 同步队列：管理获取失败的线程

如果 线程A 已经拿到锁了，此时线程B 应该进入 同步等待队列，并在适当的时机挂起。

AQS 内部使用**基于节点的双向链表**结构组织同步等待队列。

可以将它简化理解为：

```text
             AQS 同步等待队列

head  <-->  Node(B)  <-->  Node(C)
               |             |
             线程 B        线程 C
```

其中，每个等待节点记录了与线程等待相关的信息，包括线程引用、节点链接以及等待状态等。

假设线程 A 持有锁，线程 B 和线程 C 依次获取失败。 它们就可能进入同步等待队列：

```text
线程 A：持有锁，执行临界区代码

同步队列：
head <--> Node(B) <--> Node(C)
```

这里的 `head` 是队列管理使用的头节点，不应简单理解为当前持有锁的线程。

在适当的条件下，等待线程可以通过 `LockSupport.park()` 挂起，不再持续执行 CAS 消耗 CPU。

当锁被释放后，AQS 会协调等待队列中的线程重新尝试获取同步状态。

这样一来，CAS 负责安全地修改同步状态，而同步队列负责组织竞争失败的线程。



## 4. AQS 如何获取锁？

在理解了 AQS 的核心组成后，我们可以分析获取锁的全过程：

以 ReentrantLock 这种非公平锁为例：

```java
ReentrantLock lock = new ReentrantLock();
lock.lock();
try{
    //临界区代码
}finally {
    lock.unlock();
}
```

调用lock（）时 ，同步器会尝试获得同步状态。

若获取成功，线程进入临界区执行代码

若失败，AQS需要协调线程进入等待队列。

## 4.1  第一步：尝试获取锁

在 ReentrantLock 的逻辑中，锁没有被持有时，可以通过 CAS 将state 从 0 修改为1 ，

```java
if(compareAndSetState(0,1)){
	//获取锁成功
}
```

实际实现还需要记录锁的持有线程，并处理可重入情况。

锁被持有时，其他请求获取锁的线程调用lock（） 获取失败进入等待机制。

## 4.2 第二步： 进入同步队列

这里要注意一个问题： **为什么线程获取锁失败以后不是 LockSupprot.park()挂起，而是先进入同步等待队列？**

AQS不仅要让线程等待，还要维护线程之间的等待关系，协调后续的唤醒。

而且，线程在获取失败进入等待会列和准备挂起的时候，锁可能被释放出来，如果刚获取失败的时候所就被释放了，被挂起就会浪费获取锁的机会。

因此，AQS 会在等待流程中重新检查同步状态，并通过节点状态和唤醒协议协调线程挂起，避免发生不正确的等待。

### 4.3 第三步：挂起等待线程

当线程 B 已经进入同步队列，并且暂时无法获取锁时，AQS 可以使用 `LockSupport.park()` 挂起当前线程。

`park()` 可以使当前线程暂停执行，等待后续被唤醒或其他允许返回的事件。相比持续执行 CAS 的自旋锁，挂起等待可以避免线程在较长的等待时间内不断占用 CPU。

但需要注意，`park()` 并不保证一定要等到其他线程调用 `unpark()` 才返回 （ 线程被挂起的过程一直在park（）之中）。线程中断、虚假唤醒也可能使他 返回。

### 4.4 第四步：被唤醒后重新竞争锁

线程 被唤醒后，会继续执行获取流程，并重新尝试获取锁。 但这只代表了由获取锁的机会，而不是直接获取到了锁。此时有其他的线程到达，会参与竞争锁并有可能成功。


## 5. AQS如何释放锁？

AQS 的两个重要方法： 

* tryRelease(): 具体的同步器定义规则
* release() ： AQS组织释放后的等待线程唤醒流程

对于 可重入锁，线程如果连续获得了两次锁，调用unlock（） 会让state -1 ，直到state归零，锁才会完全释放。当锁真正释放成功后，AQS 会根据等待队列的状态，尝试唤醒合适的后继线程。

```text
线程 A 调用 unlock()
          |
          v
执行 tryRelease()
          |
          v
减少锁的重入次数
          |
          v
判断是否完全释放
          |
     +----+----+
     |         |
     否        是
     |         |
     v         v
  仍持有锁   释放成功
               |
               v
        检查同步等待队列
               |
               v
        唤醒合适的等待线程
               |
               v
        等待线程重新尝试获取锁
```

## 6. AQS 的独占模式与共享模式

AQS 除了 服务上述的互斥锁 （独占模式），还有共享模式。**共享模式允许多个线程在满足同步条件时同时成功获取资源**，典型代表是 `Semaphore`。

```java
Semaphore semaphore = new Semaphore(3);
```

这里的信号量容许三个许可，线程获取一个许可之后，可用许可就会减少。只要还有可用许可，其他线程可以继续获取。许可耗尽后，后续获取就需要进入等待。和 可重入锁不同，Semaphore 的state 表示许可数量，AQS为共享模式提供了 acquireShared()、 releaseShared() 等基础方法，此外还需要解决一个问题：当资源允许多个线程继续获取时，如何传播唤醒 使后续的等待线程可以有机会继续执行。

## 7. AQS 的能力边界

### 7.1 AQS 不保证所有同步器都是公平的

非公平锁允许新到达的线程在某些情况下直接竞争锁，即使同步队列中已经存在等待线程。 公平锁则在获取逻辑中考虑是否存在排在前面的等待线程，尽量按照等待顺序分配锁。但公平锁也不是绝对意义上的严格先来先服务。例如，`tryLock()` 的无参形式不受公平策略的排队约束。

因此，公平性并不是 AQS 自动赋予所有同步器的性质，而是由具体同步器的获取策略决定。
### 7.2 线程阻塞和唤醒也存在开销

虽然AQS通过等待队列和挂起机制减少了CPU 的损耗，但是 线程挂起、唤醒以及后续的调度都可能产生开销。在锁持有时间较短、竞争程度低的情况下，cpu 的损耗 不大 ， 直接获取锁比进入阻塞状态更合适。

### 7.3 AQS 不能自动保证业务逻辑正确

业务代码出现锁使用不当、锁的顺序不一致、未释放锁等问题，仍会出现错误。使用 `try-finally` 可以保证正常的异常退出路径也会执行释放操作，是使用显式锁时的重要习惯。正确使用锁仍然需要合理设计临界区范围、锁的获取顺序以及异常处理逻辑。


## 8. 总结：

AQS 是应对CAS 在锁竞争程度大、 持有锁时间长的场景下 的一种解决方案，不让其他的线程空转cpu 就把他们放入 等待队列里并协调管理阻塞和唤醒状态。AQS 将这些通用机制抽象出来，形成了一套可以复用的同步框架。其中：

- `state` 用于记录同步状态。
- CAS 等原子操作用于安全地协调状态更新。
- 同步等待队列用于组织获取失败的线程。
- `LockSupport.park()` 和 `unpark()` 等机制用于支持线程等待与唤醒。
- 具体同步器负责定义资源如何获取和释放。

因此，AQS 并不是简单地把 CAS 和一个队列组合起来，而是围绕同步状态建立了一整套线程协调机制。

从 `volatile` 到 CAS，再到 AQS，我们实际上在逐步解决不同层次的并发问题：

**volatile 解决共享状态的可见性与有序性问题，CAS 提供原子的条件更新能力，而 AQS 则在这些基础机制之上，进一步解决线程竞争、排队、阻塞与唤醒的问题。**

理解 AQS，最重要的是回答三个问题：

1. 为什么 CAS 可以实现最简单的自旋锁，却不足以高效管理长时间的锁竞争？
2. AQS 如何通过同步队列协调获取失败的线程？
3. 为什么线程被唤醒之后，仍然需要重新尝试获取同步状态？
