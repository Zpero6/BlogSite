# 有了Volatile 为什么还要加锁？

在并发编程种，因为有多线程的出现，程序的共享变量在同一时间可能被多个线程同时访问和修改。这个时候会诞生一个问题：
多个线程同时看见并同时修改变量，如何保证变量被正确的读取和更新？

## 1. Volatile 能做到什么？


### 1.1 保证可见性

```java
public class VisibilityDemo {
    private static boolean running = true;

    public static void main(String[] args) {
        Thread worker = new Thread(() -> {
            while (running) {
                // 持续执行任务
            }
            System.out.println("线程结束");
        });

        worker.start();

        running = false;
    }
}
```

正常情况下，我们希望主线程将 `running` 修改为 `false` 后，工作线程能够退出循环。

当  主线程 读取 running  的值并写入 后，B并不知道值已经变动了，这说明  worker 线程中 的count 和 真正的count 已经不是同一个变量了，**worker线程中的是一份缓存副本。**

但由于没有建立线程间的同步关系，Java 内存模型并不保证worker线程一定能观察到这个修改。编译器或 JVM 也可能对循环中的读取进行优化。

因此，工作线程可能一直循环。

那么如果让 主线程把结果写入内存的时候， worker线程  中  running  失效，必须去主内存中重新 读取。那么worker就会以新的count值计算，这个过程就被解决了。 这就是Volatile **保证可见性**的工作原理。


### 1.2 保证有序性

除此之外，现代编译器和CPU 对指令有运行优化机制，指令会出现重排序，比如  int a = 1 ， b = 2， c= a+b， 可能排序成 b=2，a=1，c=a+b。

但是说线程下会出现 一个情况：

```java
// 假设有两个变量被A、B 线程共享
int data = 0;
boolean ready = false;
```

线程 A：

```java
data = 100;     // ①
ready = true;   // ②
```

线程 B：

```java
if (ready) {
    System.out.println(data);
}
```

正常情况下，你希望：

```txt
线程 A：
data = 100
    ↓
ready = true
    ↓
线程 B：
检测 ready == true
    ↓
输出 100
```

但由于没有同步措施，线程 B 可能观察到：

```txt
线程 A：
ready = true
    ↓
线程 B：
检测 ready == true
    ↓
输出 0
```



在A内部 data =100 和 ready = true 不存在依赖关系，可能被调整执行顺序。 这样B 可能看到ready 的新值，却没看到data 的新值。

**但是，**为了保证 多线程 语句之间的执行先后顺序，Volatile 给变量添了两堵墙： 

```java
语句1
--------- 上界
volatile 语句2
---------  下界
语句3
```

语句1 无法同通过上界，语句3 无法通过下界，这样语句的执行顺序就被固定下来了，在拿到 语句2 的值时，语句1 的值就是新值。这就是 Volatile **保证有序性**的原理， 也叫保证了  happens-before 关系。

> [!Note] 
>
> Volatile 维持的==happens-before== 关系
>
> ![volatile 的 happens-before 关系](/images/blog/volatile-why-lock/happens-before.png)
>
> - `volatile` 写具有 Release（释放）语义，保证它之前的普通读写不会被重排序到该写之后。
> - `volatile` 读具有 Acquire（获取）语义，保证它之后的普通读写不会被重排序到该读之前。



## 2. volatile 的能力边界：为什么还需要锁？

前面我们介绍了 `volatile` 的可见性、有序性，以及 happens-before 关系。

到这里似乎已经解决了多线程访问共享变量的问题：既然一个线程修改变量后，其他线程能够看到，并且指令的执行顺序也受到了约束，那么是不是只需要给共享变量添加 `volatile`，就能保证线程安全？

**答案是否定的。**

### 2.1 可见性不等于原子性

回到文章开头的计数器问题：

```java
private volatile int count = 0;

public void increment() {
    count++;
}
```

假设两个线程 A、B 分别执行一次 `count++`，理论上最终结果应该是 2。

但即使使用了 `volatile`，最终结果仍然可能是 1。

这是因为 `count++` 虽然在 Java 代码中只有一行，但它并不是一个不可分割的操作，而是由三个步骤组成：

1. 读取 `count` 的值。
2. 将读取到的值加 1。
3. 把计算结果写回 `count`。

考虑下面的执行顺序：

| 步骤 | 线程 A           | 线程 B           | count |
| ---- | ---------------- | ---------------- | ----- |
| 1    | 读取 0           | —                | 0     |
| 2    | —                | 读取 0           | 0     |
| 3    | 计算 0+1，写入 1 | —                | 1     |
| 4    | —                | 计算 0+1，写入 1 | 1     |

这里需要注意，线程 B 在 A 写入之前就已经读取到了 `count = 0`。

因此，即使 A 的写入对 B 可见，也无法改变 B 已经读取到的旧值。`volatile` 不会强制 B 在写回之前重新读取并计算。

最终，两个线程分别完成了一次自增，但计数器只增加了 1。

**问题不在于线程 B 看不到线程 A 的修改，而在于两个线程的读取、计算和写入操作发生了交错。**

这就是 `volatile` 的能力边界：

它可以保证单次读写的可见性，并提供一定的有序性保证，但无法让多个操作作为一个整体不可分割地执行。

### 2.2 如果不允许线程交错修改呢？

既然问题出在多个线程可以交错执行 `count++`，那么能不能规定：

**线程 A 执行** `**count++**` **的过程中，不允许线程 B 同时执行这个操作，必须等 A 执行完之后，B 才能继续？**

这样一来，整个过程就变成了：

```
线程 A 获取执行权限
    ↓
读取 count = 0
    ↓
计算 0 + 1
    ↓
写入 count = 1
    ↓
线程 A 释放执行权限
    ↓
线程 B 获取执行权限
    ↓
读取 count = 1
    ↓
计算 1 + 1
    ↓
写入 count = 2
```

只要保证两个线程不能同时进入这段代码，就不会发生前面那种更新丢失的问题。

这实际上就是**互斥（Mutual Exclusion）**的思想。

在 Java 中，我们可以使用锁来实现互斥。

### 2.3 synchronized：让复合操作具有原子性

例如，使用 `synchronized` 修改计数器：

```java
private int count = 0;

public synchronized void increment() {
    count++;
}
```

这里的 `synchronized` 使用当前对象的监视器锁。

当线程 A 获取锁并进入 `increment()` 后，线程 B 如果也想通过同一个对象调用这个同步方法，就必须等待 A 释放锁。

即使线程 A 在执行 `count++` 的过程中发生了 CPU 线程切换，只要锁没有被释放，线程 B 就无法进入受同一把锁保护的临界区。

因此，读取、计算和写入这三个步骤虽然在底层仍然是多个操作，但对其他遵守同一锁规则的线程来说，它们被保护成了一个不可交错执行的整体。

这就是锁提供的原子性保证。

需要注意，锁并不会让 `count++` 在硬件层面变成一条原子指令，而是通过互斥访问保证临界区内的操作不会受到其他持有同一把锁的线程干扰。

### 2.4 锁只保证原子性吗？

不是。

除了通过互斥访问保证临界区的原子性，`synchronized` 还提供可见性和有序性保证。

根据 Java 内存模型：

**对一个监视器锁的解锁，happens-before 后续对同一个监视器锁的加锁。**

因此，线程 A 在同步代码块中完成修改并释放锁后，线程 B 随后获取同一把锁，就能够观察到 A 在释放锁之前的修改。

所以，我们可以这样理解：

- `volatile`：适用于状态标志、线程间通知等不依赖复合操作原子性的场景。
- `synchronized`：适用于需要多个线程互斥访问共享状态的场景。
- `ReentrantLock`：同样可以实现互斥，并提供可中断获取锁、限时尝试获取锁、公平锁等更灵活的控制能力。
- `AtomicInteger`：对于简单计数等场景，可以通过原子操作避免显式加锁。

### 2.5 小结

到这里，我们就可以回答最初的问题：

**既然有了 volatile，为什么还需要锁？**

因为多线程环境中的线程安全问题不仅仅是可见性问题，还包括多个操作之间的原子性和共享状态的一致性问题。

`volatile` 可以保证特定的可见性与有序性约束，但无法阻止多个线程交错执行复合操作。

而锁通过互斥机制，将需要整体执行的代码保护起来，同时建立相应的 happens-before 关系。

**所以，volatile 和锁并不是互相替代的关系，而是针对不同并发需求提供的同步机制。**
