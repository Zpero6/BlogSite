# Java 并发编程：线程池是如何管理线程与任务的？

在 Java 中，我们可以通过 `Thread` 创建线程，让多个任务并发执行。

例如：

```
for (int i = 0; i < 100; i++) {
    new Thread(() -> {
        // 执行业务任务
    }).start();
}
```

这段代码为每个任务创建一个独立线程。 当任务数量较少时，这种方式似乎没有什么问题。但如果系统每秒需要处理成千上万个任务呢？

每创建一个线程，JVM 和操作系统都需要为其分配相应资源。线程数量过多，还会增加上下文切换和调度开销。更重要的是，任务数量往往由外部请求决定。如果每来一个请求就创建一个线程，那么系统就缺少了**对并发数量的有效控制**。

因此，我们需要一种机制：

- 复用已经创建的线程，避免反复创建和销毁。
- 限制同时存在的工作线程数量。
- 暂时保存来不及执行的任务。
- 当系统无法继续接收任务时，采取明确的处理策略。

这就是线程池要解决的问题。

## 1. 线程池是什么？

线程池是一种管理和复用线程的机制。与每次执行任务都创建新线程不同，线程池会维护一定数量的工作线程，由这些线程不断从任务队列中获取任务并执行。

例如：

```java
ExecutorService executor = Executors.newFixedThreadPool(3);

for (int i = 0; i < 10; i++) {
    executor.execute(() -> {
        System.out.println(Thread.currentThread().getName());
    });
}

executor.shutdown();
```

这里创建了一个固定大小为 3 的线程池，并向其中提交了 10 个任务。

线程池不会为每个任务都创建一个独立线程，而是使用最多 3 个工作线程执行这些任务。

当某个工作线程完成任务后，可以继续执行其他任务。

需要注意，线程池管理的是**线程资源**，而任务只是等待或正在执行的工作单元。

线程与任务并不是一一对应的关系。

## 2. ThreadPoolExecutor 的核心参数

Java 提供了 `ThreadPoolExecutor` 类，可以通过构造方法配置线程池的行为。

例如：

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2,
    4,
    60,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(2),
    Executors.defaultThreadFactory(),
    new ThreadPoolExecutor.AbortPolicy()
);
```

这个构造方法包含七个参数：

| 参数              | 含义             |
| ----------------- | ---------------- |
| `corePoolSize`    | 核心线程数       |
| `maximumPoolSize` | 最大线程数       |
| `keepAliveTime`   | 空闲线程存活时间 |
| `unit`            | 时间单位         |
| `workQueue`       | 任务等待队列     |
| `threadFactory`   | 线程工厂         |
| `handler`         | 拒绝策略         |

其中，最需要理解的是核心线程数、最大线程数和任务等待队列之间的关系。

### 2.1 核心线程数

`corePoolSize` 表示线程池优先维持的工作线程数量。默认情况下，如果当前工作线程数小于核心线程数，新任务提交时，线程池会优先创建新的工作线程执行任务。例如：

```
corePoolSize = 2;
```

当线程池刚刚创建时，通常并不会立即创建两个线程。只有任务提交后，线程池才会根据需要创建工作线程。当然，也可以通过 `prestartCoreThread()` 或 `prestartAllCoreThreads()` 提前启动核心线程。

需要注意，核心线程并不是一种特殊的线程类型，而是线程池用于控制工作线程数量的一个阈值。

### 2.2 最大线程数

`maximumPoolSize` 表示线程池允许存在的工作线程数量上限。例如：

```
maximumPoolSize = 4;
```

意味着线程池最多可以同时维护 4 个工作线程。但这不意味着提交第 3 个任务时，就一定会创建第 3 个线程。因为 `ThreadPoolExecutor` 会优先考虑任务等待队列。只有当队列无法继续接收任务，并且当前工作线程数还没有达到最大线程数时，线程池才会尝试创建额外的工作线程。

### 2.3 任务等待队列

当工作线程数已经达到核心线程数后，新提交的任务通常会优先尝试进入等待队列。例如：

```
new ArrayBlockingQueue<>(2);
```

这里创建了一个容量为 2 的有界阻塞队列。当工作线程暂时无法处理新任务时，任务可以先进入队列，等待空闲线程取出执行。需要注意：

**等待队列存储的是尚未开始执行的任务，而不是正在等待获取锁的线程。**

它与 AQS 中管理线程竞争的同步队列不是同一种概念。

## 3. 线程池如何处理提交的任务？

假设线程池配置如下：

```
核心线程数：2
最大线程数：4
等待队列容量：2
```

现在连续提交 7 个任务，并假设所有任务执行时间都很长，在提交过程中没有任务完成。线程池会如何处理？

| 任务   | 处理方式         | 工作线程数 | 队列任务数 |
| ------ | ---------------- | ---------- | ---------- |
| 任务 1 | 创建核心工作线程 | 1          | 0          |
| 任务 2 | 创建核心工作线程 | 2          | 0          |
| 任务 3 | 进入等待队列     | 2          | 1          |
| 任务 4 | 进入等待队列     | 2          | 2          |
| 任务 5 | 创建额外工作线程 | 3          | 2          |
| 任务 6 | 创建额外工作线程 | 4          | 2          |
| 任务 7 | 触发拒绝策略     | 4          | 2          |

从这个例子可以看出，线程池并不是一开始就创建到最大线程数。

它遵循一套明确的任务接收流程。

### 3.1 第一步：优先创建核心线程

当新任务提交时，线程池首先检查当前工作线程数是否小于 `corePoolSize`。

如果小于，就尝试创建新的工作线程执行任务。

### 3.2 第二步：尝试进入等待队列

当工作线程数已经达到核心线程数后，线程池会尝试将新任务加入 `workQueue`。

如果入队成功，任务就等待后续由工作线程执行。

### 3.3 第三步：队列已满，尝试扩容线程

如果等待队列无法接收任务，线程池就会检查当前工作线程数是否小于 `maximumPoolSize`。

如果仍有扩容空间，就尝试创建额外的工作线程执行任务。

### 3.4 第四步：触发拒绝策略

线程池已经达到最大工作线程数，而且任务队列也无法接收新任务，那么线程池就要拒绝此次任务提交。可以将正常运行状态下的处理流程概括为：

```
提交任务
    |
    v
工作线程数 < corePoolSize？
    |
    +-- 是 --> 创建核心工作线程
    |
    v
尝试加入任务队列
    |
    +-- 成功 --> 等待工作线程执行
    |
    v
队列无法接收
    |
    v
工作线程数 < maximumPoolSize？
    |
    +-- 是 --> 创建额外工作线程
    |
    v
执行拒绝策略
```

这里描述的是正常运行状态下的简化逻辑。实际实现还需要处理线程池关闭、并发状态变化等问题。**线程池的核心调度思想，就是利用线程数量和等待队列共同控制任务的执行速度与资源占用。**

## 4. 为什么需要拒绝策略？

线程池虽然能够复用线程，但它的处理能力并不是无限的。假设系统每秒只能处理 100 个任务，但外部每秒提交 1000 个任务。即使使用线程池，任务也会不断积压。如果允许任务无限排队，最终可能造成内存占用持续增长，甚至发生内存溢出。因此，线程池需要一种机制，在无法继续接收任务时明确决定如何处理。Java 的 `ThreadPoolExecutor` 提供了四种内置拒绝策略。

### 4.1 AbortPolicy：抛出异常

```
new ThreadPoolExecutor.AbortPolicy()
```

当线程池无法接收任务时，直接抛出 `RejectedExecutionException`。这是 `ThreadPoolExecutor` 的默认拒绝策略。它的优点是让调用方明确感知任务提交失败，而不是悄悄丢弃任务。

### 4.2 CallerRunsPolicy：调用者执行

```
new ThreadPoolExecutor.CallerRunsPolicy()
```

如果线程池尚未关闭，则由提交任务的线程自己执行任务。例如，原本由业务线程向线程池提交任务，但线程池已经满载。此时业务线程需要亲自执行该任务，从而减慢后续任务的提交速度。这可以形成一种简单的反压效果。但如果线程池已经关闭，该策略会直接丢弃任务。

### 4.3 DiscardPolicy：直接丢弃

```
new ThreadPoolExecutor.DiscardPolicy()
```

直接丢弃无法接收的任务，不抛出异常。这种策略只适合允许任务丢失的场景。对于订单处理、支付等重要业务，通常不应该采用静默丢弃策略。

### 4.4 DiscardOldestPolicy：丢弃队列头部任务

```
new ThreadPoolExecutor.DiscardOldestPolicy()
```

当线程池尚未关闭时，尝试移除等待队列头部的任务，然后重新提交当前任务。需要注意，丢弃的是队列头部任务，而不是正在执行的任务。如果队列采用优先级排序，队列头部也不一定是提交时间最早的任务。

四种拒绝策略可以概括为：

| 策略                | 处理方式               |
| ------------------- | ---------------------- |
| AbortPolicy         | 抛出异常               |
| CallerRunsPolicy    | 调用者执行             |
| DiscardPolicy       | 直接丢弃               |
| DiscardOldestPolicy | 丢弃队列头部任务并重试 |

此外，线程池已经进入关闭状态时，新任务同样可能触发拒绝策略。因此，拒绝任务并不一定意味着线程池的线程数和任务队列都已经满了。

## 5. 线程池中的线程如何复用？

前面介绍了线程池如何接收任务。

但还有一个问题：**线程池为什么能够让同一个线程反复执行不同任务？**关键在于 `ThreadPoolExecutor` 内部的工作线程机制。

线程池使用 `Worker` 管理工作线程。一个工作线程在执行完当前任务后，并不会立即结束，而是继续尝试从任务队列中获取下一个任务。其核心思想可以简化为：

```java
while (task != null || (task = getTask()) != null) {
    try {
        task.run();
    } finally {
        task = null;
    }
}
```

这段代码只是为了说明工作线程的任务循环，并非完整的 JDK 源码。实际的 `runWorker()` 还包含线程状态、锁、异常处理和统计信息维护等逻辑。

当工作线程执行完一个任务后，会继续调用 `getTask()` 获取下一个任务。如果队列中存在等待任务，就可以继续执行。如果暂时没有任务，工作线程可能阻塞等待新任务。因此，线程池并不是让一个线程同时执行多个任务，而是让同一个线程在不同时间依次执行多个任务。这就是线程复用的基本原理。

## 6. 核心线程会一直存在吗？

默认情况下，核心线程通常不会因为空闲超时而被回收。而超过核心线程数的工作线程，在空闲时间超过 `keepAliveTime` 后，可以被回收。例如：

```
new ThreadPoolExecutor(
    2,
    4,
    60,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(10)
);
```

假设线程池在高峰期创建了 4 个工作线程。当任务逐渐减少后，超过核心线程数的工作线程如果持续空闲，就可能在 60 秒后退出。线程池最终可以收缩到核心线程数附近。

不过，`ThreadPoolExecutor` 还提供了：

```
executor.allowCoreThreadTimeOut(true);
```

开启后，核心线程也允许因为空闲超时而被回收。

因此，**核心线程数不是线程池必须始终保持的线程数量，而是线程池管理工作线程的一个重要阈值。**

## 7. 为什么不推荐直接使用 Executors 创建所有线程池？

Java 提供了多个创建线程池的便捷方法，例如：

```
Executors.newFixedThreadPool(10);
Executors.newCachedThreadPool();
Executors.newSingleThreadExecutor();
```

这些方法使用方便，但部分默认配置可能隐藏资源风险。

### 7.1 FixedThreadPool：任务队列可能持续增长

`newFixedThreadPool()` 使用固定数量的工作线程，并采用无界容量的 `LinkedBlockingQueue`。

如果任务提交速度长期高于处理速度，等待队列就可能不断增长。

由于队列通常不会因为容量已满而拒绝任务，线程池也不会依靠队列满来创建超过核心线程数的工作线程。

因此，过多任务可能造成较高的内存占用。

### 7.2 CachedThreadPool：线程数量可能持续增长

`newCachedThreadPool()` 使用 `SynchronousQueue`，不通过普通容量队列缓存等待任务。

当没有可用的空闲线程接收任务时，线程池可能创建新的工作线程。

它的最大线程数配置为 `Integer.MAX_VALUE`。

如果大量任务持续提交，而且执行时间较长，就可能创建大量线程，造成资源压力。

### 7.3 更推荐显式配置 ThreadPoolExecutor

在需要控制资源上限的业务场景中，直接创建 `ThreadPoolExecutor` 更容易明确线程池的容量与拒绝行为。

例如：

```
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    4,
    8,
    60,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),
    Executors.defaultThreadFactory(),
    new ThreadPoolExecutor.AbortPolicy()
);
```

这里明确配置了核心线程数、最大线程数、队列容量和拒绝策略。

但这些参数并不是通用的最佳配置。

实际设置时，需要根据任务类型、执行时间、请求量和机器资源进行评估。

## 8. 线程池什么时候会关闭？

线程池并不会因为某个任务执行完成就自动关闭。一般情况下，线程池会继续等待新的任务。只有发生明确的生命周期变化时，线程池才会进入关闭状态。例如：

```
executor.shutdown();
```

`shutdown()` 会让线程池停止接收新任务，但已经提交的任务仍然可以继续执行。而：

```
executor.shutdownNow();
```

则会尝试中断正在执行的任务，并返回尚未开始执行的任务列表。需要注意，`shutdownNow()` 并不能保证正在执行的任务立即终止，因为线程中断是一种协作机制。此外，如果线程池由 Spring 等框架管理，应用容器关闭时，也可能由框架负责关闭线程池。线程池是否关闭，可以通过以下方法判断：

```
executor.isShutdown();
executor.isTerminated();
```

其中：

- `isShutdown()`：是否已经发起关闭。
- `isTerminated()`：关闭后，所有任务是否已经结束。

**工作线程因为空闲超时退出，不等于线程池已经关闭。**

## 9. 线程池参数应该如何设置？

线程池的参数配置需要结合任务特点，而不是简单套用固定公式。一般可以先将任务分为两类。

### 9.1 CPU 密集型任务

例如：

- 大量数学计算。
- 数据编码与解码。
- 复杂算法处理。

这类任务主要消耗 CPU 计算资源。

如果线程数量远超 CPU 可并行执行的数量，就可能增加上下文切换开销，而不一定提高吞吐量。

因此，CPU 密集型任务通常不需要创建过多工作线程。

### 9.2 I/O 密集型任务

例如：

- 调用远程 HTTP 接口。
- 查询数据库。
- 读取文件或网络数据。

这类任务可能在等待 I/O 结果时阻塞。

如果使用传统阻塞式 I/O，适当增加线程数量，可以让部分线程等待 I/O 时，其他线程继续执行任务。

但这并不意味着 I/O 密集型线程池越大越好。

线程数量仍然受到内存、数据库连接池、下游服务处理能力等资源限制。

因此，线程池参数应该结合实际负载测试和监控数据调整。

对于业务系统，还需要重点关注任务队列长度、任务等待时间、任务执行时间和拒绝次数。

## 10. 总结

回到文章最初的问题：

**为什么不能为每个任务都创建一个线程，而需要使用线程池？**

因为线程本身是一种需要消耗系统资源的执行单元。

如果线程数量完全由外部任务数量决定，就可能导致资源占用失控。

线程池通过复用工作线程、限制线程数量和缓冲等待任务，将任务提交与任务执行分离，实现对并发资源的统一管理。

其中：

- `corePoolSize` 决定线程池优先创建的工作线程数量。
- `maximumPoolSize` 限制线程池允许存在的最大工作线程数量。
- `workQueue` 负责缓存暂时无法执行的任务。
- `keepAliveTime` 用于控制部分空闲工作线程的回收。
- `RejectedExecutionHandler` 决定线程池无法接收任务时如何处理。

理解线程池，最重要的是回答三个问题：

1. **任务提交后，为什么先创建核心线程，再进入队列，最后才扩容到最大线程数？**
2. **线程池如何让一个工作线程反复执行多个任务？**
3. **当任务提交速度超过处理能力时，线程池如何避免资源无限增长？**

线程池的本质并不是简单地把线程放在一个集合中反复使用，而是通过线程数量、任务队列和拒绝策略，共同控制系统的并发执行能力。

理解这一点，才能真正掌握 `ThreadPoolExecutor` 的设计思想。
